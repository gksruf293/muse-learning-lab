# Claude 디자인 의뢰 맥락

## 목표

Muse는 한국어 개인 학습 블로그이자 학습 기록 도구입니다. 사용자는 무료 공개 문서를 하루 한 시간씩 읽고 실제 실습 후 자신의 말로 답합니다. **읽기 → 실습 → 이해 확인 → 완료 → 답변과 AI 리뷰 다시 보기**가 핵심입니다. 기능 구현 후 시각 디자인을 Claude에게 맡기기로 했습니다.

저장소: https://github.com/gksruf293/muse-learning-lab

공개 사이트: https://gksruf293.github.io/muse-learning-lab/

현재 로컬 위치: `C:\CV\muse-learning-lab`

학습 자료, 완료 답변, 리뷰는 사용자가 모두 공개로 선택했습니다. 다른 비공개 저장소의 건강·일정·지원서 문맥은 이 프로젝트에 가져오지 않습니다.

## 현재 구현

- 의존성 없는 HTML/CSS/JavaScript 정적 앱.
- 4개 학습 문서: SQL 조회, Python sqlite3 저장, HTTP 요청/응답, FastAPI 첫 API.
- 문서당 60분: 목표 5분, 원문 20분, 실습 20분, 질문 15분.
- 원문을 검토한 날짜와 실제 읽은 구간, 링크를 표시.
- 질문 3개, 답변 자동 초안 저장, 실습 메모.
- **그날의 학습 완료** 버튼.
- 답변 파일 다운로드, 수동 AI 리뷰 프롬프트 복사.
- 답변을 쓰기 전 정답을 노출하지 않도록 평가 기준을 접어 둠.
- 학습 기록 목록을 펼쳐 답변·리뷰 열람.
- 자료 보관함: 링크와 목적 메모, 새 학습 문서 생성 프롬프트.
- PC 연결 상태와 공개 페이지/PC 화면의 저장 방식 차이 표시.
- 안내 페이지.

화면은 작동 가능한 기본 디자인입니다. 새 시각 디자인은 자유롭게 제안하되 기존 상태·인터페이스를 보존하세요.

## 기술 구조

| 경로 | 역할 |
|---|---|
| `docs/index.html` | 화면 골격, 접근성 landmark, 주요 섹션 |
| `docs/assets/style.css` | 색·글꼴·간격·반응형 스타일 |
| `docs/assets/app.mjs` | 학습 문서·폼·기록·자료 보관함 렌더링 |
| `docs/assets/core.mjs` | payload 검증, Issue 직렬화, 리뷰 프롬프트 |
| `docs/data/lessons.json` | 학습 원문 링크·설명·실습·질문·평가 기준 |
| `docs/data/config.json` | 공개 저장소·계정·PC 화면 주소 |
| `docs/guide.html` | 실제 연결 방법과 제한 안내 |
| `scripts/server.mjs` | PC 로컬 API와 같은 학습 화면 제공 |
| `scripts/worker.mjs` | 순차 리뷰·중복 방지·실패 후 재시도 |
| `scripts/runtime.mjs` | GitHub CLI/AI CLI 실행, 로그인 계정 확인 |
| `start-local.ps1` | Windows 설치 경로·기존 로그인 연결 후 실행 |
| `.github/workflows/pages.yml` | 검사·GitHub Pages 배포 |
| `tests/learning.test.mjs` | 저장 형식·보안 경계·리뷰 재시도 검사 |

GitHub Pages는 `docs/`만 배포합니다. 정적 앱에 모델 키나 GitHub 쓰기 토큰을 넣지 않습니다. 리뷰는 GitHub Actions가 아니라 **사용자의 PC에 설치된 Claude/Codex CLI**가 작성합니다. 기본 모델은 CLI 설정을 따릅니다. OpenRouter를 사용할 수 있다는 답변이 있었지만 사용자는 이후 리뷰도 PC CLI를 쓰도록 명확히 정정했습니다. API 키 기반 방식으로 되돌리지 마세요.

## 저장과 실행 계약

PC 화면은 `GET /api/status`로 연결 상태와 로컬 세션을 확인합니다. 완료 시 `POST /api/drafts`로 답변을 보관하고 `POST /api/complete`로 `{submissionId}` 완료 신호를 보냅니다. 서버가 `gh issue create/edit`로 공개 저장하고 리뷰 프로그램을 깨웁니다. 리뷰 프로그램은 `gh issue list`로 새 학습 기록을 확인하고 AI CLI 출력 후 `gh issue comment`로 게시합니다.

공개 페이지는 PC 명령을 직접 실행할 수 없습니다. 완료 버튼은 GitHub의 미리 채운 새 Issue 저장 링크를 제공합니다. 사용자가 최종 저장 버튼을 누른 뒤 PC가 켜져 있으면 리뷰가 처리됩니다. 긴 답변은 Markdown 다운로드+붙여 넣기 흐름을 사용합니다. 이 단계를 가리거나 아직 저장하지 않은 답변을 ‘저장 완료’로 표시하지 마세요.

`muse-submission` HTML 주석의 JSON payload와 `muse-review:<SHA256>` 댓글 표시가 데이터를 연결합니다. 이 형식을 바꾸려면 파서·서버·테스트를 함께 바꿔야 합니다. 답변을 변경하면 새 리뷰가 필요합니다. 사용자 입력과 리뷰는 `textContent`로 안전하게 표시합니다. HTML/Markdown 렌더러를 추가한다면 XSS 처리를 반드시 함께 구현하세요.

초안은 기기별 localStorage에 있고 동기화되지 않습니다. GitHub에 저장한 완료 기록만 기기 간 공유됩니다. PC가 꺼짐/절전/인터넷 단절/CLI 로그인 만료/사용 한도 도달 상태에서 즉시 리뷰를 약속하지 마세요.

## 디자인 요청

1. 공부하기 좋은 한국어 읽기 화면으로 개선하세요. 본문 행 길이·줄 간격·한글 글꼴·코드 가독성을 먼저 설계하세요.
2. 학습 블로그의 느낌을 살리되 자료와 답변을 찾기 쉬운 구조로 만드세요. 대시보드 카드나 배지로 모든 정보를 잘게 쪼개지 않아도 됩니다.
3. 원문 읽기, 실습, 답변 작성, 저장 후 리뷰 상태를 명확히 구분하세요.
4. 모바일에서 긴 답변 작성과 리뷰 재열람이 편해야 합니다.
5. 색·글꼴·간격을 CSS 변수로 정리하고 키보드 포커스·명도 대비·반응형을 검수하세요.
6. 사용자가 어떤 기능을 쓸 수 있는지 판단하는 데 필요한 연결·저장 상태는 유지하세요. CLI 명령이나 데이터 형식을 학습 흐름 곳곳에 늘어놓지 마세요.
7. 학습 완료 기록·점수·연속 학습일 수·사용자 답변을 디자인용으로 지어내지 마세요. 예시 화면이 필요하면 별도 데모로 명시하세요.
8. 애니메이션은 보조로만 쓰고 `prefers-reduced-motion`을 지원하세요.
9. 데스크톱/모바일 실제 실행 화면으로 변경 결과를 보여 주세요.

색과 스타일은 제안해도 되며, 현재의 종이색·초록색 팔레트에 묶일 필요는 없습니다. 외부 폰트·이미지를 추가한다면 출처·사용 조건을 확인하세요. 새 라이브러리는 기능상 이유가 있을 때만 추가하세요.

## 변경 가능 범위와 검증

우선 변경 대상은 `docs/index.html`, `docs/assets/style.css`, `docs/assets/app.mjs`의 시각·사용성 부분, `docs/guide.html`입니다. 백엔드 구조를 바꿔야 하면 필요성을 먼저 설명하고 기존 연결 흐름을 유지하세요.

검증: `npm test`, `npm run check`, Windows `./start-local.ps1` 실행. 확인 항목: 학습 선택, 질문 접근성, 날짜별 초안 복원, 다운로드, 완료→Issue 저장, 긴 답변 대체 저장, 리뷰 대기/완료/실패 표시, 자료 보관함, 모바일 줄 넘침, 키보드 조작. 공개 배포와 실제 PC 리뷰 검증은 로그인과 CLI 서비스 사용 가능 상태에서 확인하세요.

최종 결과물에는 바꾼 파일, 변경 이유, 실행·검사 결과, 남은 제한을 적어 주세요. 실제 사용자 답변을 대신 만들거나 실제 학습이 끝난 것처럼 기록하지 마세요.
